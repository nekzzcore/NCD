# Компактный профиль и поиск по обычному никнейму

SQL в Supabase и деплой не запускались. Production не изменён.

## Интерфейс

В шапке профиля — аватар и обычный никнейм с существующими кнопками выбора фото
и редактирования. Блок псевдонима, копирование/обновление, дополнительные поля,
видимость и сохранение псевдонима удалены из профиля и настроек. Клиентский
`public-tags.js` и его подключения/устаревшие тесты удалены. Авторизация,
сохранённый ник, аватар, статус и остальная модель данных не менялись.
Статистика профиля сохранена отдельно от компактной шапки.

Поиск друзей использует полное совпадение обычного облачного `profiles.nickname`
без учёта регистра, с удалением крайних пробелов (2–32 символа, без @, # и управляющих
символов). Одинаковые ники разрешены. Результат — аватар, никнейм и короткий ID:
`Имя · #4821`. Все совпадения доступны страницами по 50 записей через «Показать ещё».
Заявки привязаны к конкретному UUID `user_id`, а не строке никнейма/короткому ID.

Короткий ID выделяется последовательностью на сервере. Он глобально уникален,
стабилен при переименовании и недоступен для редактирования. Это минимум четыре
цифры; после 9999 длина растёт, поэтому совпадения/исчерпание четырёх цифр не возникают.
Email не используется для генерации ID, поиска или отображения результата.
ID добавляется существующим аккаунтам, новым — через серверный триггер регистрации.

Аватар выдаётся только при ранее сохранённом разрешении `avatar_public=true`.
Остальные профили показывают нейтральную аватарку: приватные фото автоматически
не публикуются. Удаление UI видимости не меняет ранее сохранённое согласие.
Никнеймы, похожие на email, не раскрываются: публичная проекция показывает
«Пользователь». Сырые профили, email, статус, заметки и финансовые данные не выдаются.

## SQL для просмотра

**`supabase/migrations/20261022_nickname_search.sql`** — отдельная идемпотентная
миграция; применяется одна, независимо от применения прошлых черновиков.
Старые `schema.sql`, миграции тегов/псевдонимов повторно запускать не нужно.
Миграция не удаляет таблицы, строки и прежние поля псевдонимов; они сохраняются
как исторические данные. Старые RPC редактирования/поиска отзываются.

Добавляется `profiles.social_short_id` с уникальным индексом. Серверные триггеры
назначают ID и запрещают изменение существующего значения. Клиентам не выдаётся
запись в колонку/последовательность. Ники продолжают изменяться обычным редактором.
RLS сохраняется; существующие owner-политики не удаляются. Ограничивающие политики
владельца и участников заявки пересекаются с существующими. Запись friendships
разрешена через RPC, лимиты поиска/заявок сохранены (20/мин и 5/мин).

RPC: `social_search_nickname(search_nickname, after_id)`,
`social_request_nickname(target_id)`, `social_people()`, `social_friend_profile(target_id)`.
Принятие/отклонение использует прежний `social_respond`. Повторная заявка идемпотентна,
заявка себе запрещена; автоматического принятия нет. Страница поиска отдаёт только
`user_id`, `short_id`, `nickname`, `avatar`; UUID нужен для выбора адресата и не показывается.

## Ручные шаги

1. На **staging** сохранить снимок схемы и политик. Выполнить только read-only
   `supabase/public-tags-preflight.sql`. Проверить `profiles.user_id/nickname`,
   существующий модуль друзей и включённый RLS. При другой схеме остановиться:
   не запускать старую полную схему и не удалять owner-политику.
2. Просмотреть и выполнить в SQL Editor staging только
   `supabase/migrations/20261022_nickname_search.sql` целиком. BEGIN/COMMIT внутри;
   повторное выполнение не меняет уже выделенные ID. Старые черновики не нужны.
3. В двух тестовых аккаунтах синхронизировать профиль обычным механизмом приложения.
   Проверить поиск уникального ника; затем назначить одинаковый ник и проверить
   два результата с разными ID. Отправить заявку выбранному аккаунту, проверить
   повтор, принятие/отклонение и запрет заявки себе. Переименовать аккаунт,
   синхронизировать: ID должен остаться прежним.
4. На обычном **изолированном пустом PostgreSQL** выполнить
   `test/public-tags-fixture.sql` → `supabase/social.sql` → новую миграцию дважды →
   `supabase/social-nickname-rls-smoke.sql`. Fixture и smoke не выполнять в production
   или в существующей базе Supabase: они предназначены для синтетических пользователей.
5. После проверки staging/RLS согласовать production отдельно. Без подтверждения
   production-миграция и деплой не выполняются.

## Что проверяется локально

- `npm test`: текущие сценарии приложения, поиск/совпадения/пагинация/точный адресат,
  повторная заявка и заявка себе; сохранение/проверки аватара и никнейма.
- `test/profile-compact.test.cjs`: реальный рендер DOM профиля с ширинами 1440 и 375,
  отсутствие псевдонимов, сохранность данных/управления и мобильные CSS-правила.
- `npm run build:web`: синтаксис JS, сборка и обновление `public`/`www`.
- `GT_TEST_POSTGRES_BIN=/absolute/path/to/native/bin npm run test:social:db`:
  реальный PostgreSQL 18, новая миграция дважды на исходной схеме друзей и поверх
  прежней миграции псевдонима; уникальный/совпадающий ник, постоянство и неизменяемость
  ID, автоматическое создание, 55 совпадений с пагинацией, приватность, конкретный
  адресат заявки, повтор/самому себе, принятие/отклонение и лимиты.
- Ограничения среды: нет доступного браузера для визуальной проверки/снимков ПК и
  телефона. RLS и Supabase HTTP/Realtime **не подтверждены**: серверные сокеты
  запрещены, а standalone PostgreSQL обходит RLS. Поэтому функциональный SQL-тест
  не выдаётся за проверку RLS; отдельный smoke требует обычного сервера.
