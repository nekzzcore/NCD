# Публичные теги: изменения и применение

Миграция подготовлена, **в Supabase не выполнялась**. Production и деплой не изменялись.
Git-метаданных в этом каталоге нет. Исходники перед изменениями сохранены в
`/home/sayonara/AI-Workspace/public-tags-before`; сравнение делается с этой копией.

## Что меняется

- `profiles.public_tag`: уникальный тег, хранится без `@`, в нижнем регистре, без пробелов.
  Формат: 3–40 символов `a-z`, `0-9`, `_`, первый символ — буква. `@` нужен только
  для отображения. `#` и поиск по части отображаемого имени не поддерживаются.
- Существующим профилям назначается `player_<uuid>`, новым — случайный `player_…`.
  Email и приватный nickname при генерации не используются.
- Публичное имя хранится отдельно в `public_display_name` (по умолчанию «Игрок»).
  `avatar_public=false` по умолчанию. Аватар выдаётся только после согласия владельца.
- Уникальность контролирует индекс PostgreSQL; конфликт возвращает `tag_taken`.
  `public_tag_custom` отличает предложенный тег от подтверждённого пользователем.
- Поиск: `social_search_tag(search_tag)` → состояние и максимум один профиль
  с `user_id`, `public_tag`, `display_name`, `avatar`. Нет доступа к email и сырым JSON.
- Новые RPC: `social_identity`, `social_set_identity`, `social_search_tag`,
  `social_request_tag`, `social_friends_tag`, `social_profile_tag`.
  Старые discovery RPC отключаются отзывом EXECUTE, чтобы не оставлять обход через email/аватар.
- Заявки остаются заявками; принятие и отклонение — существующий `social_respond`.
  Повторный запрос идемпотентен; после отклонения повторная заявка запрещена 24 часа.
- Серверные лимиты на пользователя: поиск 20/мин, заявки 5/мин, изменения идентичности
  5/мин, включая занятые теги. Лимит возвращается как состояние, без отката счётчика.
- Существующие политики profiles/friendships **сохраняются**, в том числе
  `Users can manage own profile`. RLS не отключается, публичный SELECT не добавляется. Добавлены ограничивающие
  (restrictive) политики владельца профиля и участников заявки; они пересекаются
  с существующими политиками. Прямые изменения friendships отозваны, чтобы
  нельзя было обойти серверный лимит через таблицу.
  Прямой INSERT/UPDATE новых защищённых колонок отзывается; остальные колонки сохраняют
  права синхронизации. Проверка формата и лимиты выполняются через RPC.
- Авторизация по email и пароль не меняются. Выбранный при локальном создании тег
  проверяется после привязки облачного аккаунта; до этого он только предложение.

## Точные ручные шаги

1. **Сначала staging**, либо отдельный тестовый PostgreSQL. Не выполнять эти действия
   на production до отдельного подтверждения владельца.
2. Открыть нужный staging-проект → SQL Editor. Выполнить только
   `supabase/public-tags-preflight.sql` (SELECT-запросы без пользовательских данных).
   Проверить `profiles.user_id`, `nickname`, `revision`, `extra`, существующие
   `friendships`, `goals`, `user_profile` и RPC из модуля друзей. RLS profiles и
   friendships должен быть включён. Сохранить выдачу списка политик.
3. Если схема отличается (например, `profiles.id` вместо `profiles.user_id`) или нет
   модуля друзей, **остановиться и адаптировать миграцию по фактической схеме**.
   Не запускать `schema.sql` повторно и не удалять существующие политики/таблицы.
4. Просмотреть `supabase/migrations/20261020_public_tags.sql`. В SQL Editor staging
   выполнить **только этот файл целиком**; он содержит BEGIN/COMMIT. Повторное
   выполнение допустимо. Проверить неизменность существующих RLS-политик и новые RPC.
5. На обычном изолированном PostgreSQL выполнить `test/public-tags-fixture.sql`,
   затем `supabase/social.sql`, затем новую миграцию дважды и
   `supabase/public-tags-rls-smoke.sql`. Эти fixture/smoke файлы — **только для пустой
   тестовой базы**, не для production и не для существующего Supabase проекта.
   В них три синтетических UUID, без реальных email и паролей.
   Smoke проверяет, что backend действительно применяет RLS, и отказывается работать
   в standalone-режиме, где RLS обходится. В конце данные сценария откатываются.
6. Дополнительно в staging открыть приложение под двумя тестовыми аккаунтами
   (разные профили браузера). В профиле/настройках сохранить разные теги, скопировать
   их, проверить поиск без учёта регистра/пробелов, отсутствующий тег, занятый тег,
   повторную заявку, заявку себе, принятие и отклонение. Проверить приватный аватар
   и включение его публичности. Затем отключить сеть и выйти: чужие данные должны исчезнуть.
7. Только после успешных staging/RLS проверок показать результаты владельцу и
   получить **отдельное подтверждение** на production-миграцию. Применение и деплой
   в эту задачу не выполнялись.

## Локальные проверки и их ограничения

- `npm test`: интерфейс, нормализация/копирование/редактирование тега, ошибки конфигурации,
  существующие сценарии друзей и приложения. Supabase в UI-тестах имитируется.
- `npm run build:web`: синтаксис JS, сборка и копирование ассетов `public`/`www`.
- `GT_TEST_POSTGRES_BIN=/absolute/path/to/native/bin npm run test:tags:db`:
  отдельный временный кластер PostgreSQL, реальные функции/индексы/ограничения,
  миграция дважды, точный поиск/приватность, состояния заявок, принятие/отклонение,
  серверные лимиты. Системная установка PostgreSQL/libpq не нужна: используются
  бинарники и библиотеки отдельного npm-пакета в `/tmp` с локальным LD_LIBRARY_PATH.
  В конце временный кластер удаляется; сетевых соединений нет.
- Среда запрещает TCP/Unix-сокеты (`EPERM`). Поэтому здесь использован standalone
  PostgreSQL 18. Он обходит RLS: **RLS и HTTP/PostgREST/Realtime интеграция с Supabase
  реально не проверены**. Результат функционального SQL-теста не выдаётся за проверку RLS.
