# Player Tag: актуальный клиент и OTA

«Друзья» читают собственный ID прямым запросом profiles.select('id,short_id').eq('id',session.user.id). Корректный #XXXXXX76 отображается из серверной строки профиля; ID не подставляется по email и не выдумывается на клиенте. Если ID отсутствует, доступен обычный запуск сохранения собственного профиля и повторное чтение ID. Генерацию выполняют уже установленные триггеры базы. Вызова social_generate_player_tag нет.

## Поиск

Кнопка «Найти» вызывает существующую **search_profile_by_tag**. Введённый тег нормализуется к # и заглавным буквам; нужны 6–8 букв/цифр. Результат может быть массивом строк, одной строкой либо объектом profiles. Показать «Добавить в друзья» можно только при совпадении полного short_id и корректном UUID. Поиск по handle/email не выполняется.

Кнопка поиска вызывает ровно `supabase.rpc('search_profile_by_tag', { search_tag: inputValue })`. Аргумент фиксирован как search_tag; определение сигнатуры через OpenAPI, старые настройки имени параметра и сообщение «Поиск по Player Tag ещё не настроен» удалены. При реальном отказе запроса показывается ошибка соединения/поиска, а не выдуманный результат. Для этого изменения не требуются новые RPC на сервере.

## Фоновые запросы

Список отношений читается из friendships(id,requester_id,recipient_id,status), последние сообщения — из messages(id,sequence,sender_id,recipient_id,body,created_at). Доступные публичные поля профилей читаются с соблюдением существующего RLS: id,short_id,username,avatar_url. Если чужой профиль скрыт RLS, его данные не раскрываются; известный тег из результатов поиска используется из памяти текущего аккаунта. Без доступного тега отображается «ID недоступен».

Автоматических вызовов social_people_players, social_dialogs, social_friend_player_profile и social_generate_player_tag больше нет. Явные действия заявки/ответа/профиля продолжают использовать существующие серверные social_request_nickname, social_respond и social_friend_profile из исходного социального модуля.

Синхронизация использует profiles.id; JSONB-документы — user_id,data, цели — user_id и свои поля. Удалена попытка переключать profiles на несуществующий user_id. Проекции select передаются строками с реальными именами колонок, без user_id:1 и объектных алиасов.

## Подготовка и публикация

`npm run build:web` обновляет public и www.

`./deploy-update.sh --prepare-only` без доступа к облаку увеличивает patch-версию, собирает бандл, создаёт update-VERSION.zip и www/version.json с SHA-256 и проверяет целостность ZIP. Ничего не публикуется.

Публикация подготовленной версии из обычного терминала с авторизацией Wrangler: `./deploy-update.sh VERSION "Поиск по Player Tag и исправления запросов"`. При явном VERSION повторного увеличения версии нет.

Клиентские проверки: `node test/social.test.cjs`, `node test/cloud-sync.test.cjs`, `node test/ota-sync.test.cjs`. Реальная сигнатура RPC и ID в удалённом Supabase из текущей среды не проверены: DNS проекта недоступен.

## Без ID-заглушек и повторяющихся ошибок схемы

В рабочих JS/HTML нет фиксированных Player Tag: поле поиска содержит обычную текстовую подсказку, при пустом short_id отображается «Не назначен». Источник значения — прямой ответ profiles.short_id. Неудачный более поздний запрос не подавляет уже полученный успешный ответ; более старый успешный ответ не может заменить новый успешный.

Сообщения выбираются по id, sender_id, recipient_id, body, created_at. Сортировка — created_at и id, без зависимости от sequence. Курсор истории учитывает и timestamp, и id, сохраняя микросекунды timestamps. Ошибки запросов обрабатываются в try/catch. Если сервер отверг схему/колонки (400/404), автоматические повторы соответствующего запроса останавливаются до ручного «Обновить». Ошибка сообщений не скрывает список друзей. Это предотвращает повторяющиеся невалидные HTTP-запросы; браузерный журнал сетевых ошибок не подменяется.

## Изменение собственного ID без выхода

Канал «Друзей» подписан на UPDATE public.profiles с фильтром id текущего пользователя. Полученный short_id немедленно отображается и передаётся общему клиентскому состоянию. Ответы чтений, начатых до события, не могут вернуть прежний тег. При возвращении в приложение и каждые 30 секунд активного экрана выполняется контрольное чтение.

Для мгновенной доставки profiles должна быть включена в публикацию Supabase Realtime. Если это ещё не сделано, подготовлен идемпотентный SQL supabase/migrations/20261025_profiles_realtime.sql. В этой задаче SQL к удалённой базе не применялся. При отключённом Realtime остаются контрольные чтения.
