# Публичный псевдоним @имя

Подготовлены код и отдельная идемпотентная миграция. SQL в Supabase не запускался;
production, email авторизации, пароли и деплой не менялись.

## Продолжение существующей работы

Сохранена текущая реализация друзей, заявок, чата, лимитов и приватности аватара.
Псевдоним — одна строка в существующем поле `profiles.public_tag`; второе поле
идентификации не создаётся. Названия JS-файлов/колонки сохранены для совместимости,
в интерфейсе используется только слово «псевдоним».

- Формат: `@` + 3–40 латинских букв, цифр или `_`, первый символ имени — буква.
  `@Sayonara76` и `@sayonara76` — один псевдоним. Крайние пробелы убираются;
  внутренние пробелы, `#`, кириллица и email-подобные строки отклоняются.
- Псевдоним задаётся вручную в профиле; отображается отдельной строкой над никнеймом.
  Его также можно скопировать и изменить в настройках. При занятости введённая
  строка сохраняется и показывается ошибка; цифры и суффиксы не подбираются.
- Автоматическая генерация из прошлого черновика отключена. Пока пользователь
  не выбрал псевдоним, показывается «Псевдоним не задан»; поиск и новые заявки
  требуют его заполнения. Старые автоматически выданные строки остаются в базе,
  но не выдаются в поиске и не показываются как выбранные псевдонимы.
- Подтверждённые ранее значения сохраняются. Изменение псевдонима не меняет
  user_id, заявки, дружбу, переписку или email авторизации.
- Поиск строго по `@имя`; отображается псевдоним, публичный никнейм и разрешённый
  аватар. UUID используется внутри запросов и не показывается в результатах.
- Аватар приватный по умолчанию, включается владельцем. Уникальность контролирует
  уникальный индекс PostgreSQL без учёта регистра.
- Лимиты сохранены: поиск 20/мин, заявки 5/мин, изменения псевдонима 5/мин.
  После отклонения — 24 часа до повторной заявки. Самому себе заявка запрещена.
- Новые endpoints: `social_search_alias`, `social_request_alias`,
  `social_friends_alias`, `social_profile_alias`; интерфейс профиля использует
  существующие `social_identity`/`social_set_identity` с проверкой нового протокола.
  Старые discovery endpoints отзываются, чтобы не оставлять обходы.

## Миграция для просмотра

**`supabase/migrations/20261021_public_alias.sql`** — единственный актуальный файл
для ручного применения этого изменения. Он работает как до, так и после старого
черновика `20261020_public_tags.sql`. Старый файл сохранён как исторический;
применять или повторно запускать его не нужно. Не запускать весь каталог миграций
по алфавиту: это подготовленные ручные черновики, а не настроенный migration runner.

Новая миграция не удаляет данные, не отключает RLS и сохраняет существующие политики,
включая `Users can manage own profile`. Ограничивающие политики и запрет прямой
записи защищённых колонок/заявок остаются. Удаляется только генератор-триггер
`goaltracker_assign_public_tag` из предыдущего черновика; значения профилей не удаляются.
Поле допускает NULL до ручного выбора псевдонима; индекс гарантирует уникальность
всех выбранных значений. Секретов и service_role в клиенте нет.

## Ручные действия в Supabase

1. Выбрать **staging**, сохранить снимок схемы/политик. В SQL Editor выполнить
   read-only `supabase/public-tags-preflight.sql`. Сверить `profiles.user_id`,
   `friendships`, `goals`, `user_profile`, существующие RPC друзей и включённый RLS.
   Если схема отличается — остановиться и адаптировать миграцию; **не запускать
   `schema.sql` повторно**, не удалять политику `Users can manage own profile`.
2. Просмотреть и выполнить в staging **только** `20261021_public_alias.sql` целиком
   (BEGIN/COMMIT внутри). Повторное выполнение идемпотентно. Старый черновик с
   генерацией не нужен, даже если он никогда не применялся.
3. В двух тестовых аккаунтах открыть профиль: выбрать разные псевдонимы, проверить
   строку над никнеймом и копирование. Попробовать занятое имя в другом регистре:
   ожидается ошибка без добавления цифр. Проверить поиск существующего/отсутствующего
   `@имени`, отклонение строки без `@`, повторную заявку, заявку себе, принятие
   и отклонение, а также настройку публичности аватара.
4. Проверить RLS на обычном тестовом PostgreSQL. Для **пустой изолированной базы**:
   `test/public-tags-fixture.sql` → `supabase/social.sql` → новая миграция дважды →
   `supabase/public-tags-rls-smoke.sql`. Fixture/smoke не выполнять в production
   или существующем Supabase-проекте. Сценарий использует синтетические UUID без
   реальных email/паролей и проверяет доступ под разными ролями/пользователями.
5. После успешных staging/RLS проверок согласовать production отдельно. До вашего
   подтверждения production-миграция и деплой не выполняются.

## Проверки здесь

- `npm test`: тесты интерфейса/валидации и существующих сценариев приложения.
- `npm run build:web`: синтаксис JS, сборка, обновление `public` и `www`.
- `GT_TEST_POSTGRES_BIN=/absolute/path/to/native/bin npm run test:tags:db`:
  реальный изолированный PostgreSQL 18 без соединений с Supabase, применение
  новой миграции дважды на исходной схеме и поверх предыдущего черновика;
  уникальность, поиск/приватность, занятость без автосуффикса, заявки, лимиты,
  сохранение существующих значений. Используются библиотеки пакета в `/tmp`,
  системные библиотеки не устанавливаются.
- **RLS и живая интеграция Supabase здесь не подтверждены**: серверные сокеты
  запрещены средой, а standalone PostgreSQL обходит RLS. Функциональный SQL-тест
  не выдаётся за проверку RLS; отдельный RLS smoke требует обычного сервера.
