# Прямая синхронизация Supabase

Актуальный путь синхронизации данных — `sync.js`. Клиент не вызывает
`goaltracker_read_state` или `goaltracker_write_state`: отсутствие этих RPC
больше не блокирует обмен данными. SQL-схема этой правкой не менялась.

При восстановлении сессии/входе автоматически включается фоновая синхронизация.
Аккаунт определяется через `session.user.id`, а не по введённому email.
Новая локальная сессия привязывается автоматически; данные другого владельца
без явной привязки не выгружаются.

Данные читаются из `goals`, `finance_transactions`, `safety_fund`, `user_profile`
по `user_id`. Каждая цель — отдельная строка с `id` и `user_id` текущей сессии;
цели выгружаются через `upsert` с `onConflict: 'id'`, читаются постранично.
Удаление ограничено конкретным `id` и текущим `user_id`. Поля дат/родителя
сопоставляются с SQL-именами, `subgoals` (включая вложения) сохраняется как JSONB.
Финансовые транзакции также хранятся отдельными строками: id, user_id, type, amount, category, description, date. Запись использует onConflict: 'id', чтение — постраничное по user_id. Удаление ограничено id транзакции и user_id владельца. Список транзакций не отправляется как один JSONB-документ. Для safety_fund, user_profile и calendar_events новые документы создаются с `onConflict: 'user_id'`.
Уже существующие JSONB-документы обновляются условным `update`: если версия
изменилась после чтения, клиент перечитывает состояние и повторяет объединение.
Служебный `__goaltrackerVersion` находится в JSONB и не отображается в приложении.
Для массивов он хранится в первом элементе; пустой массив сравнивается с `[]`.
Это не требует новых SQL-колонок и не помещает большие Base64-вложения в URL фильтра.
Версионная защита документов рассчитана на обновлённые клиенты. У целей и транзакций используется upsert по id: одновременная запись одной строки между чтением и записью не защищена серверным compare-and-swap.

`profiles` читается через fetchProfile при каждом восстановлении сессии/входе независимо от результата загрузки финансов. Разрешены только id, username, handle, short_id; фильтр — id текущего пользователя. short_id из старого кэша сбрасывается перед начальной загрузкой и заменяется серверным значением. Метод CloudSync.fetchProfile() позволяет явно повторить чтение. short_id не передаётся при обычной записи профиля и сохраняется сервером.
Полный профиль и дополнительные финансовые/календарные данные сохраняются в user_profile.data, где __goaltrackerSync содержит financeOther и calendar. Для finance_transactions поддерживаются отдельные строки и существующий JSONB-документ с массивом операций.

Перед записью выполняется трёхстороннее объединение с последним подтверждённым
состоянием. Независимые цели/подцели объединяются по ID, удаления сохраняются.
Пересекающиеся изменения одного поля требуют выбора версии в настройках.
Подушка объединяется целиком, чтобы баланс и история не расходились.

После успешных записей выполняется повторное чтение; входящие данные сохраняются
через ProfileStorage (включая Android persistent backend) и локальное хранилище
финансов. Перерисовываются цели, финансы и содержимое аккаунта в настройках.
Изменения во время запроса сохраняются через durable receipt и повторный цикл.
Статус «Синхронизировано» появляется только после успешного подтверждения и
применения. Ошибка одного запроса оставляет локальные правки и диагностику.

Запись разных таблиц не является общей SQL-транзакцией. При частичном сбое
подтверждение не выдаётся, следующий цикл дописывает оставшиеся документы.
Старые RPC с транзакцией остались в исторических SQL-файлах, но клиент их не вызывает.
Не запускайте старую schema.sql повторно на существующем проекте.

Изменения отправляются после локального сохранения с объединением повторных
сигналов примерно за 100 мс. Получение запускается Supabase Realtime
(`postgres_changes`, фильтр текущего пользователя), при возврате фокуса/сети
и резервным опросом раз в 5 секунд. Realtime требует включения нужных таблиц
в публикацию `supabase_realtime` и подходящих RLS/прав в существующем проекте.
Эта правка не меняет серверные публикации или политики.

Приложение использует `ProfileStorage`/`app.goals` как основное локальное состояние.
Старый `gt_goals` читается только при отсутствии канонического массива целей;
сохранённый пустой массив не заменяется устаревшей копией.

Автотесты проверяют два клиента, Android-адаптер хранения, Realtime-сигналы,
сохранение подцелей/вложений, финансов, профиля, офлайн-правок, гонки версий,
частичные отказы и повторную отправку. Они не подтверждают доступность и схему
живого Supabase, RLS или отсутствие HTTP-ошибок на реальном устройстве.

Перед REST-записью created_at/updated_at и createdAt/updatedAt приводятся к ISO;
невалидные значения пропускаются. У goals upsert использует defaultToNull:false,
чтобы пропущенные колонки не подменялись NULL в пакетной записи. ID проверяются
как непустые строки без пробелов/служебных значений и не преобразуются из объектов.
Существующие строковые ID не мигрируются в UUID автоматически: если серверная
колонка требует UUID, необходима отдельная согласованная миграция связей.


## Единый SDK-клиент и чтение Player Tag

Единственный createClient находится в sync.js. Инстанс создаётся один раз за время жизни страницы и экспортируется как window.supabaseClient и CloudSync.client; CloudSync.authClient() и socialConnection().client возвращают тот же объект. Повторная настройка того же проекта, выход/вход и повторная загрузка sync.js не создают новый GoTrueClient. При выходе отключаются refresh/подписки и закрывается доступ к токенам; при новом входе используется тот же SDK-инстанс. Смена проекта/ключа сохраняется для следующего перезапуска приложения.

Открытие «Друзей» или настроек вызывает CloudSync.fetchPlayerTag(): profiles.select('short_id').eq('id',session.user.id).single(). SDK-запросы используют cache:no-store. Значение для отображения берётся только из ответа сервера текущего аккаунта. Кэш social.js больше не подменяет результат новым объектом с устаревшим ID. Порядковый номер чтения и проверка аккаунта защищают от поздних ответов. В настройках добавлено явное отображение «Ваш ID».


## Ошибки схемы при чтении

Выборки проходят через selectData с try/catch. Для отсутствующих таблиц/колонок возвращается пустой результат соответствующего типа и отмечается ошибка чтения. transactionRows читает доступные поля без обращения к OpenAPI и распознаёт существующий JSONB-документ. Неполная схема строк не считается пустыми данными: синхронизация останавливается, сохраняя локальные изменения.

Ошибка схемы не интерпретируется как успешное чтение пустого облака: полная синхронизация не применяет такой снимок и не загружает удаление/подтверждение локальных транзакций. Открытое рабочее пространство сохраняется; на новом устройстве список финансов остаётся пустым, а уже существующие несохранённые записи не уничтожаются.

## Восстановление после HTTP 401

Общий transport в `sync.js` проверяет `auth.getSession()` перед запросами REST,
Storage и Functions. Истекающий JWT обновляется через один общий
`refreshSession()`. После 401 запрос повторяется один раз; если другой запрос уже
обновил JWT, повтор использует новый токен без ещё одного refresh. Auth-запросы
не проходят эту проверку, чтобы не заблокировать внутренний lock SDK.

Публичный `sb_publishable_…` передаётся только как `apikey`. Для вошедшего
пользователя `Authorization` содержит `session.access_token`. После обновления
сессии локальные цели отправляются через `pushGoals()`, когда текущие запросы
завершены. Повторный 401 или окончательно отклонённый refresh token оставляет
локальные данные и показывает повторный вход; тот же отклонённый JWT больше не
отправляется. Повторный вход выполняет настоящую авторизацию, а не переиспользует
отклонённую сессию.

Проверка transport с поставляемым SDK и тестовым серверным ответом:
`node --test --test-isolation=none test/supabase-transport.test.cjs`.
Это не проверка живых ключей, RLS или установленной версии на другом устройстве.

Описание OpenAPI `/rest/v1/` для определения полей профиля не запрашивается: нужный формат определяется по собственной строке profiles. JSONB-документ финансов обновляется с проверкой предыдущей версии. Если таблица пуста, её формат по данным определить нельзя; клиент использует формат отдельных строк и сохраняет локальные изменения при ошибке записи.

## Изменения на нескольких устройствах

Цели, финансовые данные, заметки, события, достижения, профиль, Case/Обучение,
привычки и игровой прогресс входят в состояние аккаунта. Изменения сначала
сохраняются на устройстве, затем отправляются и подтверждаются чтением из облака.
Последняя цель удаляется в облаке только если в локальной очереди есть сохранённое
удаление относительно известной базы; пустой новый профиль или локальный сброс
не считаются удалением. Новые цели, созданные на другом устройстве, сохраняются.

При восстановлении офлайн-изменений пересечение с изменениями другого устройства
не выбирается автоматически: локальная и облачная версии сохраняются, а в
настройках появляется выбор. Быстрая запись цели предварительно сопоставляет её
с облачной версией и не перезаписывает обнаруженный конфликт. Пока есть локальные
изменения, выход сначала пытается синхронизировать их и не очищает хранилище,
если подтверждения облака нет. Настройки отдельных устройств и данные Health
Connect остаются локальными.

Важное ограничение: отдельные строки целей и транзакций пока записываются через
upsert без атомарного сравнения версии на сервере; одновременное изменение одной
строки двумя устройствами между чтением и записью может потребовать серверной
защиты. Для фактической работы оба устройства должны получить обновлённую версию,
использовать один Supabase-проект и один аккаунт; серверная схема и права должны
соответствовать клиенту.
