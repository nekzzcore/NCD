# Подключение Supabase

Публичные параметры проекта заданы в `supabase-config.js`. Приложение также работает локально без сети. Реальное облако и RLS не считаются проверенными, пока схема и проверки ниже не выполнены в вашем проекте.

1. Создайте отдельный проект Supabase либо сначала сделайте резервную копию существующей БД. Откройте SQL Editor и выполните `schema.sql`. Нужны административные права проекта в интерфейсе Supabase; публичного ключа для изменения схемы недостаточно. Секретные ключи в клиент не добавляйте.
2. В тестовом/одноразовом проекте выполните `rls-smoke.sql`: он создаёт два искусственных auth-пользователя, проверяет запрет доступа к чужим данным и к данным без входа и заканчивается ROLLBACK. Если тест завершился ошибкой, вручную выполните ROLLBACK и исправьте схему перед подключением личных данных. На существующем проекте сначала проверьте совместимость таблиц и политик; миграция намеренно останавливается при посторонних политиках.
3. В Supabase Auth включите Email/Password. При включённом Confirm email настройте Site URL и почтовую доставку; после регистрации пользователь подтверждает почту и входит с паролем. Magic Link в этой версии не используется, поэтому Electron не требует обработки redirect/deep link.
4. По умолчанию проект уже подключён через `supabase-config.js`; откройте «Настройки → Облачная синхронизация → Вход / Регистрация». Ранее сохранённая ручная конфигурация имеет приоритет, чтобы не менять аккаунт или проект существующей сессии. Для ручной смены проекта в приложении: «Настройки → Облачная синхронизация → Параметры подключения». Введите HTTPS URL проекта и публичный `anon` JWT либо `sb_publishable_...` ключ из Connect/API Keys. Ключи `service_role`, `sb_secret_...` и произвольные JWT отвергаются. Сам публичный ключ не является паролем.
5. Нажмите «☁️ Вход / Регистрация» в настройках. Войдите/зарегистрируйтесь в отдельном окне. Если на устройстве есть значимые данные, отдельно нажмите «Привязать и синхронизировать данные устройства». Это разрешает передачу целей, финансов, календаря и фото в выбранный аккаунт. Пустое устройство загружает облачное состояние автоматически.
6. Убедитесь, что включена существующая настройка автосинхронизации. Автосохранение отправляет изменения примерно через 800 мс; получение также запускается при `online`, возврате фокуса и раз в минуту. При выключенной автосинхронизации остаётся ручная кнопка.
7. Проверьте двумя тестовыми пользователями: A не видит строки B; изменение `user_id` вручную запрещено RLS. Затем двумя отдельными устройствами одного пользователя проверьте загрузку, офлайн-правки, удаление и повторный вход.

## Хранение и объединение

`profiles` — `user_id`, nickname, общая revision и вспомогательные данные. `goals`, `finance_transactions`, `safety_fund`, `user_profile` — по одному JSON-документу на пользователя с RLS `auth.uid() = user_id`. В goals хранится массив корневых целей с вложенными подцелями; в finance_transactions — массив операций; в user_profile — никнейм/статус/дата/сжатый customAvatarData. Вспомогательные финансовые данные (бюджет/инвестиции/доход) и календарь сохраняются в profiles.extra, поэтому они не теряются.

Снимки документов выбраны для совместимости с существующим локальным форматом. Это не построчная SQL-модель каждой отдельной операции: при больших историях потребуется отдельная миграция на записи/операции и пагинацию. Размеры и производительность больших профилей не измерялись.

Серверные RPC используют `security invoker`, RLS, блокировку строки и compare-and-swap revision. Чтение/запись разных доменов согласованы транзакционно. Клиент объединяет изменения относительно последней подтверждённой версии; массивы объектов объединяются по id. Удаление с неизменённой другой версией сохраняется. Пересекающиеся изменения не затираются молча: выводятся значения и выбор спорных полей. Для подушки баланс и история выбираются целиком. Перед разрешением конфликта все версии сохраняются локально. Клиент не полагается на время часов устройств.

Несинхронизированное состояние — разница текущих долговечных локальных данных и сохранённого baseline в `gt-cloud-state-v1:<project>|<account>`. После ответа сервера сохраняется receipt; изменения, внесённые во время запроса, повторно объединяются и не пропадают. Доступ к чужим строкам запрещает БД, а не только клиентский фильтр. Запросы ограничены 15 секундами; повторная попытка не добавляет повторных транзакций, поскольку отправляется состояние с устойчивыми id.

Включённая сессия хранится штатным SDK Supabase 2.118.0. Пароли не пишутся в конфигурацию/очередь/резервные копии, поля очищаются после отправки. Auth/API запросы не кэшируются Service Worker. SDK включён локально с лицензией MIT и доступен офлайн; пакеты не устанавливались. Загрузка ключа в код сборки не требуется.

Фото теперь включено в облачный DTO по явному заданию; прежний общий JSON-экспорт приложения по-прежнему не содержит фото. Локальные настройки, токены, пароли и ключи не входят в DTO синхронизации. Фото и данные в Supabase доступны владельцу через RLS; сквозное шифрование не реализовано.

Перед входящей заменой создаётся резервная копия в localStorage `gt-cloud-backup-v1:<project>|<account>`, перед разрешением конфликта — `gt-cloud-conflict-backup-v1:...`. Выход не стирает локальные данные. На устройстве, уже привязанном к другому аккаунту/проекту, передача блокируется; для другого аккаунта используйте отдельный профиль браузера. Не редактируйте один локальный профиль одновременно в нескольких вкладках: конкуренция отдельных устройств протестирована, общий локальный storage нескольких вкладок отдельным протоколом не защищён.

Локальный сброс очищает baseline синхронизации, чтобы локальное удаление профиля не стало массовым удалением облачной копии. Резервные локальные данные/фото конфликта сохраняются на устройстве и требуют обычной защиты пользовательского профиля ОС.

### Файлы подцелей

После основной схемы выполните `goal-attachments.sql` в SQL Editor того же проекта.
Скрипт создаёт (или переводит в публичный режим) бакет `goal-attachments` и разрешает
загрузку/удаление только внутри папки текущего пользователя. Публичные ссылки
доступны всем, у кого есть URL.

Войдите в облачный аккаунт и привяжите локальный профиль. В деталях цели у каждой
подцели есть скрепка; файлы отображаются под названием, крестик удаляет вложение.
Изображения открываются в диалоге, облачные документы — в новой вкладке, локальные — скачиваются.
Объекты имеют путь `user_id/goal_id/subgoal_id/unique-filename`; оригинальное имя
и публичный URL хранятся в `subgoals[].attachments[]` в JSONB-данных таблицы `goals`.
Старые `files[]` читаются без потери вложений; при изменении списка они переносятся в `attachments[]`.
При отсутствии облака/сети или ошибке загрузки файл до 2 МБ сохраняется как Base64
в `attachments[].url`; облачный лимит приложения — 10 МБ. Метаданные включают
`id`, `name`, `type`, `size`, `url`. Base64 синхронизируется вместе с JSON цели,
но автоматически не переносится в Storage после восстановления сети.
Удаление объекта из Storage выполняется после успешного локального сохранения списка.
При сбое синхронизации метаданные остаются локально для последующей синхронизации.

Для проверки на живом проекте загрузите изображение и PDF, обновите страницу,
откройте оба файла, удалите их и проверьте JSON и отсутствие объектов в Storage.
Автоматические тесты используют имитацию Storage и не меняют облачные данные.

### Друзья и личные сообщения

После `schema.sql` выполните **`social.sql`** в SQL Editor того же проекта.
Миграция добавляет `friendships`, `messages`, индексы, RLS, функции `social_*`
и публикацию обеих таблиц в Supabase Realtime. Выполните миграцию один раз до

Поиск — по полному email подтверждённого аккаунта, без выдачи списка пользователей.
Другу доступны никнейм, аватар и краткий список целей: прогресс больше нуля либо

Для реальной проверки используйте два подтверждённых аккаунта в разных профилях
браузера: найти по email → отправить заявку → принять её во втором окне → открыть
мини-профиль → отправить сообщения в обе стороны. Убедитесь в обновлении без
перезагрузки и переключении между диалогами и перепиской на мобильной ширине.
Проверьте также отклонение заявки, переподключение сети и выход из аккаунта.

`social-rls-smoke.sql` проверяет разграничение доступа с тремя временными
пользователями в отдельном тестовом проекте и откатывает транзакцию.
`test/social.test.cjs` проверяет интерфейс, отправку, дедупликацию Realtime,

### Пошаговая регистрация NCD

Перед включением регистрации с уникальными никнеймами примените
`migrations/20261024_ncd_auth_handles.sql` в SQL Editor текущего проекта.
Миграция добавляет закрытый реестр никнеймов, публичную проверку доступности,
атомарный триггер регистрации и защиту никнейма при редактировании профиля.
Существующие дублирующиеся имена не переименовываются. Таблица `profiles`,
её RLS и структура локальных данных не изменяются. Логин и сброс пароля
не требуют этой миграции. До применения регистрация останавливается на
проверке никнейма, а не сообщает ложную доступность.

Проверьте, что в Supabase Auth включён Email provider. Подтверждение почты
поддерживается: аккаунт без session показывает экран проверки почты и не
открывает рабочую область. Для проверки нужен тестовый email, которым вы
владеете; автоматические тесты не создают реальные аккаунты и не рассылают письма.


### Cloud-first аккаунты и безопасный выход

Клиент сначала скрывает рабочую область, очищает кэш прежнего пользователя и
загружает все домены с фильтром по текущему `auth.users.id`. Только после
успешной загрузки открывается интерфейс. Старые локальные записи без
совпадающего `supabaseUserId` никогда не отправляются в новый аккаунт.
Изменения активного аккаунта отправляются сразу; офлайн-outbox привязан к
проекту и user_id и восстанавливается только при совпадении владельца.

Logout удаляет локальные документы, legacy-ключи, аватары, резервные копии,
токены и данные Preferences/IndexedDB/Electron. Публичная конфигурация проекта,
тема и неперсональный маркер выхода сохраняются. Маркер не позволяет старой
сессии автоматически восстановиться после сетевой ошибки signOut. Облачные
записи при выходе не удаляются.

Примените `migrations/20261024_cloud_account_isolation.sql` в SQL Editor:
он создаёт `calendar_events(user_id, data)` с RLS и добавляет restrictive
owner-политики к таблицам аккаунта. Существующие календарные записи в
`user_profile.data.__goaltrackerSync.calendar` продолжают читаться до миграции;
после неё первая обычная запись переносит календарь в отдельный документ.
Для `profiles` поддерживается актуальный ключ `id`, а также legacy `user_id`.
Миграция не перепривязывает, не очищает и не удаляет существующие облачные данные.

Проверка публичной схемы 24.10.2026: в текущем проекте отсутствует
`calendar_events`, а `finance_transactions` и `safety_fund` не имеют столбца
`data`, требуемого существующим документным протоколом клиента. Миграция выше
добавляет календарь и RLS, но не преобразует финансовые таблицы. Перед запуском
нужно отдельно согласовать и мигрировать существующие финансовые строки в
документы `user_id, data` без потери записей и с уникальным `user_id`.
Клиент запрашивает эти столбцы явно и блокирует рабочую область при
несовместимой схеме, вместо отображения ложного пустого баланса.

### Проверка email на первом шаге

Перед выпуском клиента примените `migrations/20261024_ncd_auth_email.sql`
в SQL Editor текущего проекта. RPC `ncd_email_available` проверяет точный
email без учёта регистра непосредственно в `auth.users`, включая аккаунты
без подтверждения почты, и возвращает только boolean. RPC вызывается с `{ check_email: email }`. При отсутствии RPC, сбое сети
или ответе не boolean регистрация остаётся на шаге email. Только `true`
разрешает переход к никнейму; `false` показывает предложение войти. Вход и восстановление пароля не вызывают эту функцию.

Для немедленного входа после регистрации в Supabase Auth должен быть выключен
Confirm email. Если подтверждение включено, Supabase не выдаёт сессию до
подтверждения: клиент сохраняет экран проверки почты. При получении сессии
клиент сохраняет токены и открывает рабочую область до облачной загрузки.
Сбой фоновой синхронизации не закрывает приложение и не открывает форму входа.
Перед открытием очищаются данные прежнего аккаунта. Правки во время загрузки
объединяются с облаком, а при сбое остаются в outbox текущего пользователя.
